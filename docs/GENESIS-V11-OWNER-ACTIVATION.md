## Implemented workflow

The new migration is `20261114184238_ares_genesis_owner_approval_v11.sql`. It extends the existing V11 certificate system and the existing private `genesis_v10` registries. It contains no seeded owner, route, entitlement, certificate or approval.

1. A database administrator verifies the genuine BOBU owner Auth user and enrolls that UUID in private `genesis_v11.owners`. Service-role and player clients cannot enroll themselves. A colony member is not automatically a world owner. Do not impersonate an identity or manufacture a JWT.
2. A trusted BOBU operator assembles a complete proposal with a fresh `ares_genesis_world_snapshot_v11()` result, full source/live occupancy, full landmark extents, external route records, exact allocation/mapping and real archived HTTPS evidence. The evidence digest identifies that actual archive. The proposal ID must equal `site.ownerProposalId`. `scripts/genesis-verify-owner-proposal.mjs proposal.json` checks the shipped terrain, complete campus envelope, source/live obstacle inventory, route/site agreement, route terrain slopes and collisions. It never grants authority. The operator remains responsible for truthful complete-world/route provenance and archive verification; boolean completeness claims are not independent evidence.
3. Service authority inserts this immutable proposal in `genesis_v11.proposals`. Server validation rejects stale snapshots, missing required inventories, route/site mismatches, invalid geometry and campus conflicts. The exact legal region is required. Incomplete recovery packages cannot satisfy this schema.
4. The genuine authenticated owner reads `get_ares_genesis_owner_proposal_v11(proposal)` and calls `decide_ares_genesis_owner_proposal_v11(proposal, approve)`. A decision is immutable and bound to the entire exact proposal. Changed or expired proposals require a new review. Rejection cannot be overwritten.
5. Service authority calls `issue_ares_genesis_owner_certificate_v11(proposal)`. In one transaction it checks owner approval/freshness, locks the current world tables, inserts the real world/mapping/entitlement/route/site-allocation records and issues through the existing V11 certificate triggers. Direct certificate inserts also require the matching owner decision. Failure rolls back all registry and certificate changes. Unrelated pre-existing authority is never overwritten. An already-issued proposal cannot be replayed. A freshly approved proposal can renew the identical route allocation issued by this workflow, atomically revoking the preceding certificate and retaining its history.
6. With a genuine player access token in `GENESIS_PLAYER_ACCESS_TOKEN` and the project publishable key in `GENESIS_PUBLISHABLE_KEY`, run `node scripts/genesis-live-approval.mjs`. This read-only script verifies the user through Auth, reads their actual colony, calls the production RPC and validates identity, release digest, lease and geometry. It logs no access token and performs no login impersonation. A blocked response fails verification.
7. The owner can call `withdraw_ares_genesis_owner_certificate_v11(proposal)` to revoke. Existing 60-second lease draining and collision guards remain. Changing authority records or disabling an owner invalidates the monotonic world snapshot. Removing protection or changing conflicting terrain still requires draining leases.

Issuance deliberately refuses to adopt an unrelated existing legacy world allocation or singleton site authority. Renewal verifies the previous issuance and registry provenance and permits the same external route inventory. Changing that inventory or reconciling unrelated historical authority requires a separate reviewed reconciliation and lease draining; no blanket upsert or destructive cleanup is implemented. The existing V11 service revocation path remains available. This migration does not enable the legacy `rpc_readiness` gate, whose diagnostic function hardcodes `fully_authorized=false`; the deployed V11 client uses its existing authenticated certificate RPC.
